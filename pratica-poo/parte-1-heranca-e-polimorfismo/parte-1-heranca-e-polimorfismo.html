Capítulo 1

O problema

Antes de aprender coisa nova, você vai sentir falta dela. Este capítulo é um desafio sem ajuda. Faça primeiro, leia o capítulo 2 depois.

O desafio

O seu jogo tem uma classe Personagem só. Todo mundo é igual, muda só os números.

Acrescente dois personagens novos ao jogo:

  • Um Guerreiro: mais vida e mais ataque que o normal, e o ataque dele nunca erra.
  • Um Mago: pouca vida e pouca defesa, mas quando ele defende, também recupera 10 de vida.

Regra do desafio: use só o que você já sabe. Não pesquise, não pule para o capítulo 2.

Checkpoint 1

O Guerreiro e o Mago funcionam no jogo. O ataque do Guerreiro nunca erra. A defesa do Mago cura 10 de vida.

Não importa se o código ficou feio. Ficar feio é o resultado esperado.

Só continue depois de tentar

Existem dois caminhos para resolver isso com o que você já sabe, e os dois têm o mesmo defeito. Provavelmente você usou um deles.

Caminho 1: copiar a classe inteira

class Guerreiro:

        self.nome = nome
        self.vida = vida
        self.vida_maxima = vida
        self.ataque = ataque
        self.defesa = defesa
        self.pocoes = pocoes
        self.defendendo = False

    def mostrar_status(self):        # igual ao Personagem
        ...
    def esta_vivo(self):             # igual ao Personagem
        ...
    def receber_dano(self, quantidade):  # igual ao Personagem
        ...
    def usar_pocao(self):            # igual ao Personagem
        ...
    def atacar(self, alvo):          # SO ESTE muda
        ...

Caminho 2: encher a classe de if

class Personagem:
    def __init__(self, nome, vida, ataque, defesa, pocoes, tipo):
        ...
        self.tipo = tipo

    def atacar(self, alvo):
        if self.tipo == "guerreiro":
            # nunca erra
            ...
        else:
            rolagem = random.randint(1, 20)
            ...

    def defender(self):
        if self.tipo == "mago":
            self.vida = self.vida + 10
        self.defendendo = True

Por que os dois são ruins

Responda para você mesmo, olhando o seu código:

  1. Se você mudar a fórmula do dano, quantos lugares precisa editar no caminho 1?
  2. Quantos if o método atacar vai ter quando o jogo tiver seis tipos de personagem?
  3. No caminho 2, o Mago recebeu um atributo tipo. O Goblin também. O Goblin precisa dele?

O caminho 1 duplica código. O caminho 2 junta comportamentos diferentes dentro do mesmo método, e ele cresce sem parar.

Python tem uma ferramenta para exatamente este problema. É o próximo capítulo.

Terminou? Este capítulo não tem extras. Os extras começam no checkpoint 2, quando você já tiver herança na mão.

Capítulo 2

Herança

Herança é dizer que uma classe é um tipo de outra. O Guerreiro é um Personagem. Ele ganha tudo que o Personagem tem, de graça, e só escreve o que for diferente.

A sintaxe é o nome da classe-mãe entre parênteses:

class Guerreiro(Personagem):
    ...

Lê-se: "Guerreiro é um Personagem".

Passo 1: o arquivo

Crie um arquivo novo chamado classes.py, na mesma pasta do personagem.py. Comece importando a classe-mãe:

from personagem import Personagem


class Guerreiro(Personagem):
    pass

O pass quer dizer "por enquanto, nada aqui dentro". Mesmo vazia, essa classe já funciona:

g = Guerreiro("Thoric", 120, 18, 8, 2)
g.mostrar_status()

Saída


 Thoric
Vida: 120 / 120
Poções: 2

Você não escreveu mostrar_status no Guerreiro. Ele veio do Personagem. Isso é herança.

Passo 2: o construtor próprio

Do jeito acima, quem cria um Guerreiro ainda precisa digitar os cinco números. Mas todo Guerreiro tem os mesmos números. Quem deveria saber disso é a classe, não quem usa.

class Guerreiro(Personagem):
    def __init__(self, nome):
        super().__init__(nome, 120, 18, 8, 2)

Agora criar um Guerreiro é só:

g = Guerreiro("Thoric")

O que super() faz

super() é uma forma de chamar a classe-mãe de dentro da filha.

Quando você escreve super().__init__(nome, 120, 18, 8, 2), você está dizendo: "Personagem, monte o objeto do jeito que você já sabe, com estes valores". O __init__ do Personagem roda e cria self.nome, self.vida, self.vida_maxima, self.defendendo e todo o resto.

Sem essa linha, nada disso é criado. O objeto nasce vazio.

Ordem importa

Chame super().__init__(...) na primeira linha do seu __init__. Só depois acrescente atributos novos. Se você inverter, o atributo novo pode ser apagado quando a classe-mãe montar o objeto.

Passo 3: o Mago

Faça o mesmo com o Mago. Ele é frágil: pouca vida, pouco ataque, pouca defesa, mas começa com mais poções.

class Mago(Personagem):
    def __init__(self, nome):
        super().__init__(nome, 70, 10, 3, 4)

Checkpoint 2

No arquivo classes.py existem as classes Guerreiro e Mago. As duas herdam de Personagem. As duas chamam super().__init__(...).

Criar um deles precisa de um argumento só: o nome.

O personagem.py não foi alterado.

Teste do checkpoint 2

Abra o personagem.py e acrescente esta linha no fim do __init__ da classe Personagem:

        self.nivel = 1

Salve. Agora rode:

g = Guerreiro("Thoric")
print(g.nivel)

Resultado esperado: aparece 1 na tela.

Se der AttributeError: o seu Guerreiro não está chamando super().__init__(...). Provavelmente você copiou as linhas do __init__ do Personagem para dentro do Guerreiro, em vez de chamar a classe-mãe. Isso funciona por acaso, mas não é herança: o Guerreiro não recebe nada que você acrescentar no Personagem depois.

Depois do teste, pode apagar a linha self.nivel = 1.

Capítulo 3

Sobrescrever métodos

Até agora as suas classes só mudam os números. O Guerreiro e o Mago lutam igual ao Personagem comum. Neste capítulo eles ganham comportamento próprio.

Sobrescrever é escrever, na classe filha, um método com o mesmo nome de um método da classe-mãe. Quando você chamar esse método no objeto da filha, a versão dela é que roda.

Existem duas situações, e elas se resolvem de formas diferentes.

SituaçãoO que fazerRegra
SubstituirNão chama super()O comportamento é outro. Você joga fora o da mãe.
EstenderChama super()O comportamento é o mesmo, mais um pouco.

Substituir: o ataque do Guerreiro

O ataque do Personagem erra quando a rolagem é menor que 5. O Guerreiro nunca erra. Isso é um comportamento diferente, não um acréscimo. Então você escreve o método inteiro e não chama super().

Este é o método original, no personagem.py:

    def atacar(self, alvo):
        rolagem = random.randint(1, 20)

        if rolagem < 5:
            print(self.nome, "errou o ataque")
            return

        dano = random.randint(self.ataque - 3, self.ataque + 3)
        alvo.receber_dano(dano)
        print(self.nome, "causou", dano, "de dano")

No classes.py, dentro da classe Guerreiro:

    def atacar(self, alvo):
        dano = random.randint(self.ataque - 3, self.ataque + 3)
        alvo.receber_dano(dano)
        print(self.nome, "atacou sem falhar e causou", dano, "de dano")

Não tem a rolagem e não tem o return. O Guerreiro sempre acerta.

O classes.py agora usa random. Acrescente import random na primeira linha do arquivo, senão você vai ver NameError: name 'random' is not defined.

Estender: a defesa do Mago

O Mago defende igual a todo mundo, e mais recupera 10 de vida. A parte "igual a todo mundo" já existe. Seria desperdício reescrever.

Dentro da classe Mago:

    def defender(self):
        super().defender()
        self.vida = min(self.vida + 10, self.vida_maxima)
        print(self.nome, "recuperou 10 de vida")

A primeira linha manda o Personagem fazer a parte dele, que é ligar o self.defendendo. Depois o Mago acrescenta a cura.

O min(...) impede a vida de passar do máximo.

Como decidir

Pergunte: "o que a classe-mãe faz ainda precisa acontecer?" Se sim, chame super(). Se não, não chame.

Checkpoint 3

O Guerreiro sobrescreve atacar e nunca erra.

O Mago sobrescreve defender, chama super().defender() e recupera 10 de vida.

O personagem.py continua sem alteração.

Teste do checkpoint 3

Rode isto:

m.vida = 50
m.defender()

Resultado esperado:

Capítulo 4

Polimorfismo

Este capítulo tem pouco código novo. O que muda é o que você vai entender sobre o código que já existe.

Passo 1: os inimigos também viram classes

No main.py, os inimigos hoje são três Personagens com números diferentes:

    inimigos = [
        Personagem("Goblin", 40, 8, 2, 0),
        Personagem("Orc", 70, 12, 4, 0),
        Personagem("Troll", 100, 16, 6, 0),
    ]

Transforme cada um em uma classe, no classes.py:

class Goblin(Personagem):
    def __init__(self):
        super().__init__("Goblin", 40, 8, 2, 0)


class Orc(Personagem):
    def __init__(self):
        super().__init__("Orc", 70, 12, 4, 0)


class Troll(Personagem):
    def __init__(self):
        super().__init__("Troll", 100, 16, 6, 0)

    def atacar(self, alvo):          # o Troll bate com tudo, mas erra muito
        rolagem = random.randint(1, 20)
        if rolagem < 9:
            print("O Troll errou feio")
            return
        dano = random.randint(self.ataque, self.ataque + 10)
        alvo.receber_dano(dano)
        print("O Troll acertou um golpe de", dano)

E no main.py:

    inimigos = [Goblin(), Orc(), Troll()]

Passo 2: olhe o laço de combate

Agora vem a parte importante. Abra o main.py e olhe o laço:

    for inimigo in inimigos:
        venceu = combate(jogador, inimigo)
        if not venceu:
            break

E dentro do combate:

        if inimigo.esta_vivo():
            inimigo.atacar(jogador)

Você acabou de dar comportamentos diferentes para três classes diferentes. Quantas linhas desse laço você precisou mudar?

Nenhuma.

O laço escreve inimigo.atacar(jogador) e não sabe se o inimigo é Goblin, Orc ou Troll. Cada objeto sabe atacar do seu próprio jeito. Quem chama não precisa perguntar o tipo, não precisa de if, não precisa saber que o Troll existe.

Isso é polimorfismo. A mesma chamada, inimigo.atacar(...), produz comportamentos diferentes dependendo do objeto que está ali.

Compare com o caminho 2 do capítulo 1, aquele cheio de if self.tipo ==. Lá, cada tipo novo obrigava a mexer no método. Aqui, cada tipo novo é uma classe nova e o resto do programa não fica sabendo.

Checkpoint 4

Goblin, Orc e Troll são classes que herdam de Personagem.

O main.py cria a lista com [Goblin(), Orc(), Troll()].

O jogo roda do começo ao fim e o Troll ataca diferente dos outros.

Você não escreveu nenhum if novo dentro de combate.

Teste do checkpoint 4

Este é o teste de verdade do polimorfismo. Crie mais um inimigo, no classes.py:

class Esqueleto(Personagem):
    def __init__(self):
        super().__init__("Esqueleto", 55, 11, 3, 0)

    def receber_dano(self, quantidade):
        print("Os ossos rangem")
        super().receber_dano(quantidade)

Agora acrescente Esqueleto() na lista de inimigos do main.py e jogue.

Resultado esperado: o Esqueleto entra na fila de inimigos, imprime "Os ossos rangem" toda vez que apanha, e o jogo funciona normalmente.

A pergunta do teste: fora a linha da lista, quantos arquivos e quantas funções você precisou modificar para o Esqueleto existir?

A resposta certa é nenhuma. Se você precisou mexer no combate ou no turno_do_jogador, alguma coisa não está herdando direito.

Capítulo 5

Fechamento

O que você construiu

Você começou com uma classe e um jogo em que todo mundo lutava igual. Agora tem uma família de classes:

Personagem
├── Guerreiro   (ataca sem errar)
├── Mago        (defende e cura)
├── Goblin
├── Orc
└── Troll       (ataca forte e erra muito)

E o mais importante: o personagem.py está do jeito que estava no Dia 5. Você não precisou reescrever nada para estender tudo.

As três ideias, em uma frase cada

IdeiaEm uma frase
HerançaUma classe é um tipo de outra e ganha tudo que ela tem.
super()Chama a versão da classe-mãe, de dentro da filha.
PolimorfismoA mesma chamada faz coisas diferentes conforme o objeto, e quem chama não precisa saber qual é.

Um cuidado antes da parte 2

Herança é "é um"

Só use herança quando a frase "X é um Y" fizer sentido. Guerreiro é um Personagem: pode. Poção não é um Personagem, mesmo que poção também tenha nome. Se a frase soar estranha, você quer um atributo, não uma classe filha.

E não empilhe. Personagem → Guerreiro é o bastante. Se você criar Personagem → Humano → Guerreiro → GuerreiroDeElite, daqui a duas semanas ninguém acha mais onde um método foi definido.

O que vem na parte 2

  • Encapsulamento: por que inimigo.vida = -999 devia ser proibido, e como o objeto se protege.
  • Seleção de personagem: o jogador escolhe entre Guerreiro e Mago no início. Isso é polimorfismo virando tela de menu.
  • Chefe final com mecânica própria.
  • O jogo fechado, do início ao fim.

Anexo A

Erros que você vai ver

Estes cinco erros aparecem para quase todo mundo. Ver o erro não quer dizer que você errou feio: quer dizer que chegou na parte difícil. Ache a mensagem aqui e siga a instrução.

1. object has no attribute

AttributeError: 'Guerreiro' object has no attribute 'nome'

O objeto foi criado sem passar pelo __init__ do Personagem. Quase sempre é um __init__ na filha que não chama super().__init__(...).

Errado

class Guerreiro(Personagem):
    def __init__(self, nome):
        pass                # nao monta nada

Certo

class Guerreiro(Personagem):
    def __init__(self, nome):
        super().__init__(nome, 120, 18, 8, 2)

2. takes 2 positional arguments but 6 were given

TypeError: Guerreiro.__init__() takes 2 positional arguments but 6 were given

O seu Guerreiro.__init__ pede só o nome, mas você criou o objeto passando cinco valores, como fazia antes.

g = Guerreiro("Thoric", 120, 18, 8, 2)
g = Guerreiro("Thoric")

Os números agora ficam dentro da classe. É esse o ganho.

3. missing required positional arguments

TypeError: Personagem.__init__() missing 4 required positional arguments:
'vida', 'ataque', 'defesa', and 'pocoes'

O contrário do anterior. A sua classe filha ainda não tem __init__ próprio, então ela usa o do Personagem, que exige os cinco valores.

Ou você escreve o __init__ da filha, ou passa os cinco na hora de criar.

4. name 'Personagem' is not defined

NameError: name 'Personagem' is not defined

Faltou o import no topo do classes.py:

from personagem import Personagem

Se a mensagem falar de random, falta import random no mesmo lugar.

5. O método existe mas não roda

Sem erro nenhum, e mesmo assim o Guerreiro continua errando o ataque. Duas causas:

  • Indentação. O def atacar ficou fora da classe. Ele precisa estar recuado quatro espaços, alinhado com o def __init__.
  • Nome diferente. Atacar ou atacaR não sobrescrevem atacar. Python diferencia maiúscula de minúscula, então você criou um método novo em vez de substituir o antigo.

Anexo C

Glossário

Os termos que apareceram na teoria, com o código deste material do lado.

TermoO que é
ClasseO molde. Personagem é uma classe.
ObjetoUma coisa feita a partir do molde. Guerreiro("Thoric") produz um objeto.
InstânciaOutro nome para objeto. "Thoric é uma instância de Guerreiro."
InstanciarCriar o objeto a partir da classe. É o que acontece quando você escreve Guerreiro("Thoric").
AtributoUm dado guardado no objeto. self.vida, self.nome.
MétodoUma função que pertence a uma classe. atacar, defender.
FunçãoUm bloco de código com nome, que não pertence a nenhuma classe. combate(...) no main.py.
ConstrutorO __init__. Roda sozinho quando o objeto é criado.
selfDentro de um método, é o próprio objeto em que o método foi chamado.
Classe-mãeA classe de quem se herda. Também chamada de superclasse ou classe base. Personagem.
Classe filhaA que herda. Também chamada de subclasse ou classe derivada. Guerreiro.
HerançaUma classe ganhar os atributos e métodos de outra.
SobrescreverA filha escrever um método com o mesmo nome de um da mãe, para mudar o comportamento.
super()Chamar a versão da classe-mãe de dentro da filha.
PolimorfismoA mesma chamada de método produzir comportamentos diferentes conforme o objeto.
EncapsulamentoO objeto proteger o próprio estado, deixando que mudanças passem só pelos métodos dele. É o tema da parte 2.
